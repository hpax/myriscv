Pipeline stages:

	F1 - Fetch - generate instruction fetch address
	F2 - Fetch - receive fetch data
	D  - Decode
	E  - Execute (address generation, ALU)
	M  - Memory accress (load, store; late ALU operations)
	W  - Write Back (register file is written)
	X  - Pseudo-stage beyond the end of the pipeline

X is not a stage per se, but an artificial name for a source for
bypass data due to the register file begin read already during the D
stage.

The split between the F1 and F2 stages is internal to the fetch unit;
the global pipeline logic consider it a single "F stage."

A clocked register is named with the stage for which its output is
valid for. Combinatorial signals become valid during their signal
stage; that is:

	- Registers inputs should be from a previous stage than the
	  register is named;
	- Combinatorial signals carry the same name as the register
	  outputs that feed hem;

Any other connections are bypasses and should be noted as such.

The valid bit propagates down the pipe and indicates whether the input
of that pipeline stage represents a valid instruction.

The E stage is the last stage in which an operation can be aborted. An
instruction allowed to advance to the M stage must retire.

Bypasses and latencies:

	E -> E		1 cycle	 (immediate use)
	M -> E		2 cycles
	E -> F1		5 cycles (mispredict kill)	XXX: correct?
	M -> F1		6 cycles (exception kill)	XXX: correct?

Additional mandatory penalty cycles in the current implementation:

A jump/branch to a misaligned 32-bit instruction takes a 1-cycle
penalty.

Load data or multiply output used in the next cycle takes a 1-cycle
penalty, except for cached multiply data (typically MULH to MUL
forward.)

A memory operation which crosses a 32-bit boundary takes a 1-cycle
(one dbus transaction) penalty.


Each stage has the following handshaking signals, for the backend
stages inputs and outputs are combinatorial for the stage in
question. The F and D stages have some special tighter coupling to
allow the F stage to output data and some handshaking signals in the D
stage; thus, the fetch unit outputs e.g. d_valid_i instead of
f_valid_o.

output  valid_o

	Assert when a stage presents output signals corresponding to a
	valid (non-null) datum. It is not required that a pipeline
	stage emits a datum in response to a valid input; it is
	permitted for a stage to "eat" its input.

input	valid_i

	Asserted when the inputs to a stage represents a valid datum.

output	busy

	Assert when the stage is doing processing taking more than one
	cycle.  If busy = valid_o = 0, the stage is empty and can
	accept a datum even the next pipeline stage is stalled.

	When valid_i = 1 and busy = 0, the stage accepted a datum.

	valid_o can be asserted together with busy; this allows
	a pipeline stage to issue multiple ops/data items to the
	subsequent stage (e.g. Zcm instructions or misaligned loads.)

input	stall

	If asserted, the next stage cannot accept input at this time.
	If valid_o is asserted, the output signals must not change
	unless killed is asserted; however, a unit is allowed change
	the outputs (including valid_o) if valid_o is not already
	asserted. This allows a unit to "catch up".

	If valid_o = 1 and stall = 0, data has been accepted and the
	unit can produce the next datum or deassert valid_o.

output	kill

	Assert to void the content of the pipeline for all stages prior to
	this one, and start a new fetch. This stage can produce valid or
	invalid output to the downstream pipe as indicated by valid_o.

input	killed

	This pipeline stage and all upstream stages are being
	killed. The output will be ignored, and the stage MUST output
	valid_o = 0 no later than the next cycle, with the sole
	exception of the F stage.

	The unit MAY continue to assert busy if already asserted, but
	after the first cycle with busy = 0, the stage MUST NOT
	re-assert busy until it has accepted at least one datum
	(valid_i = 1, busy = 0.)
